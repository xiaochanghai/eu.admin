# 标准业务模块开发约定

> 状态：CURRENT
>
> 2026-09-10 项目所有者确认：AgModelConfig 采用的标准分层与基类复用方式，同样适用于后续其他普通业务模块。

## 标准实现链路

```text
业务 Controller : BaseController<...>
  → 业务 IService : IBaseServices<...>
  → 业务 Service : BaseServices<...>
  → IBaseRepository<TEntity> / BaseRepository<TEntity>
  → 现有 SqlSugar 数据访问
```

- Controller 处理 HTTP 边界，基础增删改查直接复用 BaseController，不重复设计普通 CRUD 接口。
- IService 继承 IBaseServices；实体、Base DTO、InsertInput、EditInput、View DTO 按项目现有目录和职责落位。
- Service 继承 BaseServices，通过构造函数注入 IBaseRepository 并赋给 BaseDal。标准查询、校验和持久化能力优先复用基类。
- 特殊业务规则在当前 Service 的 Add、Update 等重写方法或业务方法中处理，继续调用现有基类和仓储能力；不把业务逻辑放进 Controller。
- Service、Repository 沿用现有 Autofac 程序集自动注册，不为普通业务服务另加手动注册或加入自动注册排除名单。
- 系统模块页面优先复用 TableList、通用表单和 SmModule 元数据，不为已有动态页面能力另造独立管理页面和请求封装。

## 不重复建设存储层

- 后续普通业务模块不得再新增 `XxxStore`、`IXxxStore`，或以其他名称重复包装现有 BaseServices/BaseRepository 的同等职责。
- 不建立 `XxxServices1` 等第二套生产业务入口；维护、修复和测试围绕实际 Controller 调用的标准 Service 进行。
- 例如模型配置不再新增、恢复或扩展 ModelConfigStore/IModelConfigStore；这不是仅针对模型配置的命名限制，而是普通业务模块的通用复用原则。
- 发现能力缺口时，先读取基类及相邻模块。确有跨业务公共缺口，按 BACKEND-PLATFORM 单独评估消费者和验证范围，不在业务任务中顺手建立另一套基础设施。

## 实现边界

- 标准模式不等于照抄某个模块全部细节：是否先插入后更新、如何计算修订号、选取哪些更新字段，必须根据业务和事务要求确定。
- 认证授权、租户/公司隔离、事务原子性、审计、并发控制、日志脱敏、密钥加密和 DTO 安全边界仍必须遵守。不得为复用基类而绕过安全要求，也不得以安全为由未经确认另建平行 Store 体系。
- 自动注册可能启用 AOP，新增包含密码或 API Key 的输入时须检查服务参数日志、请求日志和 SQL 日志。自动注册不是允许记录敏感值。
- 保持异步 I/O、多数据库兼容和现有 ServiceResult 契约。新增专用业务接口时同步检查消费者，而不是复制通用 CRUD。
- 生成代码有被覆盖风险：限定生成范围，保留并复核 Service 手写重写逻辑，不批量生成或改写无关模块。

## 特殊场景与已有代码

本约定不是批量重构、删除现有 Store 或恢复历史实现的授权。已有 MCP、流式协议、外部存储适配和明确拥有边界的基础设施按其职责维护；普通业务模块不能借用这些例外新增重复存储层。确需偏离标准链路时，先向项目所有者说明现有能力为何不足、影响范围和备选方案，获得明确确认后处理。
