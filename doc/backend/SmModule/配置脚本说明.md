# SmModule 配置脚本说明

本文件解释用户提供的 SQL 快照及经明确授权生成的部署脚本。它们用于理解三表聚合、字段配置和部署顺序；除非明确标记为只读导出，否则不是当前数据库的权威导出，也不是已经批准执行的部署脚本。

生成或编辑 `SmModuleColumn.FieldType` 时，必须读取前端 [`CompDatas.tsx`](../../../eu.admin.react/src/views/system/config/form/components/CompDatas.tsx)，并遵守 [`前端表单控件类型`](../../frontend/SmModule/表单控件类型.md)。不得凭名称猜测控件类型，也不得使用该文件中已注释的候选组件。

生成栏位值时，列表页面 Column 顺序使用 `TaxisNo`，表单页面控件顺序使用 `FormTaxisNo`；实体属性、API 字段、前端字段、SQL 列名和 MySQL 物理列名均统一为 `FormTaxisNo`。`TextArea.MinRows` 只能为空或大于 0；`Align` 只能为空或使用 `left`、`center`、`right`。

## 1. 供应商等级示例

原始示例见 [`examples/供应商等级页面模块配置.sql`](examples/供应商等级页面模块配置.sql)：

- `SmModules` 使用 `BD_SUPPLIER_LEVEL_MNG` 定义页面身份、菜单路由、通用 API 地址和前端元素路径。
- `SmModuleSql` 绑定业务表 `BdSupplierLevel`，以别名 `A` 查询，并定义正常数据、回收站和默认排序规则。
- `SmModuleColumn` 配置 `CreatedTime`、`LevelNo`、`LevelName`、`Remark` 四个栏位。
- `LevelNo`、`LevelName` 参与表单且必填；`LevelNo` 额外声明唯一性；`Remark` 和 `CreatedTime` 在查询区隐藏。
- `ColumnMode` 为空时，按当前服务逻辑可同时参与列表和表单，不能把空值解释为“不启用”。

静态校验：

- `SmModules`：45 列/45 值。
- `SmModuleSql`：33 列/33 值。
- `Remark`、`LevelName`、`LevelNo`：均为 74 列/74 值。
- `CreatedTime`：74 列/73 值，缺少一个值且后续字段语义错位，原语句不可执行。

2026-08-07 的只读数据库核对用于确认现库对应记录的 `FormTaxisNo`、`DefaultValue`、`GridSpan`、`FormTitle`、`FieldType`、`DataSourceType`、`DataSource`、`ColumnMode` 等配置值。原始文件仍保留用户提供的值序列；需要可执行版本时必须从目标环境按明确列名重新导出并重新校验。

## 2. 终端客户示例

历史/迁移快照见 [`examples/终端客户页面模块配置.sql`](examples/终端客户页面模块配置.sql)：

- 脚本使用专用 API `/api/Customer` 和抽屉表单 `/basedata/customer/FormPage`。
- `SmModuleSql` 查询 `BdCustomer A`，并通过 `LEFT JOIN SmGroup B` 输出 `GroupName`。
- `GroupName/GroupId`、`DistrictName/DistrictId`、`CurrencyName/CurrencyId` 展示名称/提交 ID 配对，其中脚本使用 `ColumnMode=list/form`。
- `CustomerNo` 配置唯一性、创建/修改限制和自动编号数据源 `BdCustomerNo`。

静态校验：`SmModules` 为 45/45，`SmModuleSql` 为 33/33，14 条 `SmModuleColumn` 均为 74/74。数量匹配只证明 INSERT 结构完整，不证明关联表、数据源、权限、方言和缓存刷新在目标环境有效。

## 3. 智能体管理 MySQL 脚本

[`examples/智能体管理模块配置.MySQL.sql`](examples/智能体管理模块配置.MySQL.sql) 由默认 MSSQL 中 `AG_%` / `/agent%` 的有效模块只读导出后转换而来，包含：

- 10 条 `SmModules`（智能体管理父模块及其子模块）；
- 4 条 `SmModuleSql`；
- 45 条 `SmModuleColumn`。

脚本使用固定 GUID 保持 `SmModules.ID` 与 `SmModuleSql.ModuleId`、`SmModuleColumn.SmModuleId` 的关联，按主表、SQL 配置、列配置的顺序执行，并使用 MySQL `INSERT ... ON DUPLICATE KEY UPDATE` 支持重复部署。存储在 `FullSql` 的 SQL 已将 `dbo.` 与 `TOP (1)` 转为 MySQL 对应形式；脚本本身不包含模型密钥或其他凭据值。

该脚本只覆盖三张模块元数据表，不包含角色模块、功能权限、角色功能权限及缓存刷新。目标 MySQL 数据库必须已具备与当前实体对应的三表字段后方可执行。

当前默认 MySQL 的三张表将 `CreatedTime`、`UpdateTime` 定义为 `datetime(0)`；因此从 MSSQL 导入的毫秒会由数据库按秒级精度保存。这不影响模块运行配置，但逐字段核对时间时应按目标列精度比较。

## 4. 执行与部署边界

1. 删除顺序为 `SmModuleColumn` → `SmModuleSql` → `SmModules`，插入顺序相反；真实部署必须使用事务或提供等价的失败恢复。
2. 三表配置不包含角色模块、功能权限、角色功能权限和多语言等全部配置；三表齐全不等于用户已经可见或可操作。
3. 直接执行 SQL 不会自动调用 `ModuleInfo.Init()`、`ModuleSql.Init(Db)`、`ModuleSqlColumn.Init/Reload`；部署方案必须包含缓存刷新。
4. 身份值、组织字段、父模块 ID 和固定 GUID 属于来源环境；复制到其他环境前必须完成映射。
5. `SELECT LAST_INSERT_ID()`/`SELECT @@IDENTITY` 是生成器输出的身份读取语句；本聚合使用显式 Guid 主键，跨数据库迁移时必须重新审查方言。
6. 未经明确写库授权，不得执行示例；获得授权后也应先在隔离环境验证。
