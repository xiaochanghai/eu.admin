# SmModule 元数据模型与维护约束

本文件适用于由 `SmModules`、`SmModuleSql`、`SmModuleColumn` 驱动的动态页面维护能力。三张表共同构成一个页面模块元数据聚合，不得按三个互不相关的 CRUD 表处理。

## 1. 事实源与关系

| 表/实体 | 职责 | 与模块主表的关系 |
|---|---|---|
| [`SmModules`](../../../eu.core/EU.Core.Model/Entity/SM/SmModules.cs) | 页面/模块身份、`ModuleCode`、菜单路由、API 地址、打开方式、页面能力开关、主从关系和工作流开关 | 聚合根，主键 `SmModules.ID` |
| [`SmModuleSql`](../../../eu.core/EU.Core.Model/Entity/SM/SmModuleSql.cs) | 主表、查询字段、连接、条件、排序、分组和完整 SQL 等数据查询模型 | `SmModuleSql.ModuleId = SmModules.ID`，每个模块零或一条 |
| [`SmModuleColumn`](../../../eu.core/EU.Core.Model/Entity/SM/SmModuleColumn.cs) | 列表列、查询项、表单控件、校验、数据源、排序、显示和导出等字段元数据 | `SmModuleColumn.SmModuleId = SmModules.ID`，每个模块零到多条 |

- `ModuleId` 与 `SmModuleId` 名称不同，但都指向 `SmModules.ID`；新增查询、复制、删除和导出逻辑不得混用。
- `SmModules.ModuleCode` 是前端和运行时缓存使用的稳定业务键；`ID` 是三表关联键，二者不得互相替代。
- `ParentId` 表示模块/菜单父子层级，`BelongModuleId` 表示从属模块关系，不得当作 SQL 或栏位配置外键。
- 三个实体均通过 `BasePoco` 间接继承 `BaseEntity`，公共字段和逻辑删除规则继续受 [`../数据库表设计约束.md`](../数据库表设计约束.md) 管理。

## 2. 页面组装链路

1. 前端使用 `ModuleCode` 调用 `GET /api/SmModule/GetModuleInfo/{moduleCode}`。
2. [`SmModulesServices.GetModuleInfo`](../../../eu.core/EU.Core.Services/SM/SmModulesServices.cs) 从模块缓存取得 `SmModules`，以其 `ID` 组装列表列、表单列、权限按钮、子模块和页面属性。
3. `SmModuleColumn` 同时驱动 `columns` 和 `formColumns`；`ColumnMode`、`TaxisNo`、`FromTaxisNo` 决定列表/表单归属和顺序。
4. `SmModuleSql` 由 `ModuleSql`/公共查询链路消费，决定列表查询的数据集、条件、排序和关联关系；它通常不直接作为页面渲染对象返回。
5. 前端将组装后的 `ModuleInfo` 按 `moduleCode` 缓存在 Redux，并由通用 Table/Form 组件消费。

单表 CRUD 成功不代表页面配置有效；三表数据、缓存和前端契约必须同时一致。

## 3. 修改硬约束

- 新增模块必须先确定唯一、稳定的 `ModuleCode`，再建立 `SmModules`；需要动态查询时建立对应 `SmModuleSql`，需要列表或表单时建立对应 `SmModuleColumn`。
- `SmModuleSql` 每个模块最多一条有效配置；`SmModuleColumn` 不得产生缺失模块、错误模块 ID 或重复冲突的有效栏位记录。
- `SmModuleColumn.DataIndex` 必须与查询结果字段/别名及表单提交字段一致；主键、主从关联字段和 `IsMasterId` 必须与真实数据模型一致。列表排序使用 `TaxisNo`，表单排序使用 `FromTaxisNo`，不得使用错误名称 `FormTaxisNo`。
- `TextArea` 的 `MinRows` 为空时由前端默认显示 3 行，显式设置时必须大于 0；列表 `Align` 仅允许 `left`、`center`、`right` 或空值，空值输出为默认 `center`。
- 修改 `SmModules.ModuleCode` 属于高影响变更，必须同步检查前端常量、路由、角色/功能权限、缓存键、SQL/栏位加载和所有仓库内调用方。
- 修改 SQL 查询字段时必须同步检查对应 `SmModuleColumn.DataIndex`；删除或改名栏位时同时检查列表、搜索、表单、导入导出、合计、跳转和工作流条件消费者。
- `SmModuleSql` 中保存的 SQL 和条件属于服务端受信配置，不得接受普通页面用户直接提供的未校验 SQL；运行时参数必须通过现有参数化/变量替换边界处理。
- 复制、导入、导出或删除模块时必须把三张表视为同一聚合，保持新 ID 映射正确且无孤儿记录。新增或修改写路径时应使用事务或提供等价的原子性与失败恢复保证。
- 文件带有代码生成标记。修改实体字段前必须确认生成器和 DTO/Input/View 派生文件的覆盖范围，不得只改一个生成结果。

## 4. 缓存一致性

| 配置变化 | 必须刷新 |
|---|---|
| `SmModules` 新增、更新、删除或 `ModuleCode` 变化 | `ModuleInfo` 缓存，以及依赖模块代码的用户/权限缓存 |
| `SmModuleSql` 新增、更新、删除 | `ModuleSql` 缓存 |
| `SmModuleColumn` 新增、更新、删除、排序或模式变化 | `ModuleSqlColumn` 缓存；已知 `moduleCode` 时优先定向 Reload |

- 不能只刷新当前 HTTP 请求内的数据；后续请求和其他宿主/实例也必须得到明确的一致性语义。
- 新增写接口时，缓存刷新是成功事务的一部分。数据库成功但缓存刷新失败时必须可观测，并说明重试或恢复方式。
- 前端已缓存的 `ModuleInfo` 不会因数据库变化自动更新；维护页面保存成功后必须触发重新获取或明确提示刷新。

## 5. 契约与验证

- 修改 `GetModuleInfo` 返回字段、大小写、可空性、`columns` 或 `formColumns` 结构时，附加 `API-CONTRACT` 和 `CROSS-END-CONTRACT`，同步更新前端 `ModuleInfo` 类型及消费者。
- 后端至少验证：模块不存在、仅主表、主表+SQL、主表+多栏位、逻辑删除栏位、列表/表单不同 `ColumnMode`、复制和缓存刷新路径。
- 前端至少验证：模块加载、列表列、查询项、表单控件、按钮权限、主从页面、空配置和配置错误状态。
- 涉及真实数据库写入的验证必须使用隔离环境并获得明确授权；纯文档或静态审查不得声称三表运行时组装已经通过。
