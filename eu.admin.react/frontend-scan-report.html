总体结论

高优先级

类型系统严重弱化

大量 any 让 React 19 + TypeScript 的收益基本被抵消。API 层、通用表格层、表单页、工作流模块是主要热点。

高优先级

业务页面重复度高

多个 FormPage.tsx 页面高度相似，只做少量字段差异化，已经形成复制式开发模式，后续维护成本会线性增加。

中优先级

副作用管理不稳

部分布局和页面的 useEffect 缺少清理或依赖收敛，存在重复注册事件、重复连接和状态漂移风险。

中优先级

通用层边界不清

通用 API、通用表格、BaseFormPage、EditableProTable 都在承载过多业务特例，抽象层逐渐变成“万能层”。

分模块扫描结果

模块 主要问题 证据 优化建议 预期结果
API 层 请求方法和返回值泛型约束弱，Record<string, any> 与 any 大量出现，业务对象缺少稳定的 DTO 定义。 src/api/modules/module.ts 中 25 处 any，queryByFilter、update、uploadFile 等方法类型宽泛。 按模块拆分 DTO 类型；把通用增删改查请求封装成强类型泛型；统一 ResultData<T> 与分页结构。 接口联调时的字段错误能在编译阶段暴露，组件层不再依赖“试出来”的数据结构。
通用表格层 表格组件承担列配置、权限、日志、导入、编辑、主从表等多种职责，形成复杂巨型组件。 src/components/ProTableEditable/index.tsx 使用大量本地状态、动态注入和 any；同类问题也出现在 src/components/ProTable/index.tsx。 拆成“数据请求”“列增强”“工具栏动作”“编辑行为”“模块权限”五类 hook 或子组件；保留外部 API，先做内部解耦。 降低单文件复杂度，减少回归风险，便于后续替换 ProTable 或接入新的页面规范。
BaseFormPage / 表单页 通用表单能力与具体业务字段耦合，多个业务 FormPage 只是复制后改少量字段逻辑。 共 20 个 FormPage.tsx；src/views/stock/in/FormPage.tsx、stock/out、stock/check、stock/accounting 结构近似。 沉淀字段依赖规则、子表列覆写、主从表默认值、保存后回填等模式，做成 schema 或 hooks；减少页面内联逻辑。 新增业务表单时更接近“配置 + 少量扩展”，复制式开发显著下降。
布局与全局副作用 SignalR 连接和事件监听逻辑有重复注册风险，调试日志直接留在运行代码里。 src/layouts/index.tsx 的 useEffect 无依赖数组且无清理，signalr.on 每次渲染都可能重复绑定。 将连接建立、重连、事件订阅封装成独立 hook；使用清理函数取消订阅；调试日志统一走开发态 logger。 减少内存泄漏、重复消息、重连异常，提升线上稳定性和问题可追踪性。
Redux 状态层 部分 slice 仍以 any 为主，状态结构不透明，难以进行安全重构。 src/redux/modules/workflow.ts、src/redux/modules/module.ts 等仍大量使用 PayloadAction<any>。 先为高频状态定义显式接口；统一模块信息、表格参数、工作流节点状态类型；收紧 action payload。 状态流转更可预期，IDE 自动补全和重构支持明显提升。
工作流 / DSL 模块 低代码与流程编辑器模块功能重，但内部类型约束不足，后续扩展会放大复杂度。 src/workflow-editor、src/workflow、src/dsl 内存在较多 any、动态结构和值对象混用。 优先梳理节点、条件、字段、表单 schema 的核心领域模型；按模型定义 reducer、渲染器和序列化结构。 复杂模块更适合做增量演进，不再依赖运行时试错判断数据合法性。
调试与遗留代码 示例代码、页面调试日志、旧版本文件残留增加阅读噪音。 全仓 47 处 console.log；存在 FormPage.old.tsx；部分页面有未清理的注释块和禁用规则。 将示例页与正式业务页隔离；删除或归档旧文件；引入统一调试开关，生产代码禁用散落日志。 代码面更干净，误读和误改概率降低，审查效率提升。

高风险问题清单

P1

重复注册 SignalR 事件

  • src/layouts/index.tsx 的副作用没有依赖控制和解绑逻辑。
  • 表现可能是重复消息、控制台刷屏、连接状态异常、性能下降。
P1

表格/表单核心层过度膨胀

  • EditableProTable 和 BaseFormPage 已经成为多个业务模式的堆叠点。
  • 任何改动都可能波及多个业务页面，回归测试范围持续扩大。
P1

类型缺失导致隐式错误

  • 1305 次 any 不是风格问题，而是使错误延迟到运行时。
  • 接口返回字段变更、列配置结构偏差、工作流节点字段缺失都可能静默通过编译。

优先级优化方案

阶段 建议动作 范围 产出
第一阶段 修复全局副作用问题，先处理 SignalR 连接、事件解绑、生产日志收敛。 layouts、utils/signalr、少量示例页 线上行为更稳定，减少重复订阅与噪音日志。
第二阶段 收紧 API 层和 Redux 层类型，优先覆盖模块信息、分页结果、表格列、表单保存结构。 src/api、src/redux、src/api/interface 建立可扩展的前端领域类型基础。
第三阶段 拆分 EditableProTable / BaseFormPage 内部职责，做 hook 化和行为插件化。 components/ProTable*、hooks/useFormPage.ts 通用层可维护性提升，后续改动影响范围缩小。
第四阶段 对重复业务 FormPage 做模板提炼，抽出主从表联动、列覆写和字段依赖规则。 views/stock、views/purchase、views/sales 减少复制代码，新增页面成本下降。
第五阶段 治理工作流和 DSL 模块类型边界，补足核心模型定义。 workflow、workflow-editor、dsl 复杂平台模块具备长期演进能力。

优化后的预期结果

稳定性

全局连接和副作用收敛后，重复事件、页面切换残留监听和不可解释的状态同步问题会明显减少。

开发效率

API 与状态类型收紧后，联调和重构将更多依赖编译器，而不是运行时试错。

维护成本

表单页和表格页从复制式开发转为模板化扩展后，新业务接入成本下降，回归面收窄。

平台化能力

工作流、表单设计、模块配置这些“平台特性”会更适合继续沉淀，而不是持续叠加临时逻辑。

建议先落地的 5 个改动

  1. 重写 src/layouts/index.tsx 的 SignalR 连接逻辑，确保只注册一次并在卸载时解绑。
  2. 为 src/api/modules/module.ts 增加分页结果、详情结果、批量操作结果类型，清理第一批 any。
  3. 把 src/hooks/useFormPage.ts 的保存、加载、状态控制拆分成更小的 hook。
  4. 从 stock/in、stock/out、stock/check 三个页面提炼公共主从表模式。
  5. 清理生产路径中的 console.log 和遗留旧文件，保留统一调试入口。
